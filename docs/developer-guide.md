# 開発者・保守ガイド

新人開発者・保守担当向けの資料です。手元で動かす方法、テスト、定期の運用、環境変数、管理者がいなくなったときの手順をまとめています。
使い方（操作者・管理者向け）は[運用マニュアル](operations-manual.md)を見てください。

## 1. 全体像

### フォルダ構成

| 場所 | 中身 |
|---|---|
| `src/` | 本番版のアプリ（Next.js の App Router） |
| `src/lib/` | 集計・CSV・AI・認証・Supabase などの処理 |
| `src/components/` | 画面の部品（ダッシュボード・アップロード・管理者・共通の ui） |
| `supabase/migrations/` | DB の構造と行レベルセキュリティ（RLS）の SQL |
| `tests/` | 単体・権限（RLS）・画面（e2e）のテスト。中身の案内は [tests/README.md](../tests/README.md) |
| `.github/workflows/` | 自動テストと公開の設定 |
| `docs/` | 説明書 |


### データの流れ

- CSV をアップロードする
- `src/lib/csv` が列名や日付の揺れをそろえ、行ごとに検査する（取り込めない行は理由つきでスキップ）
- 成功した行を、月ごとに Supabase へ保存する
- `src/lib/aggregate` が集計する（売上・粗利・リピート率・カテゴリ別・売れ筋）。**集計はここだけ**で行い、画面も AI も同じ関数の結果を使う
- 画面は集計結果を表示するだけ（画面側で計算し直さない）
- AI には集計した数字だけを送る（顧客 ID や明細の行は送らない）。返ってきた文章の金額・割合は、送った集計値と自動で照合し、合わなければ警告を出す

## 2. 手元で動かす

前提：Node.js 24.x と、検証用の Supabase プロジェクト。

| 何をする | どう操作する | OK の目安 |
|---|---|---|
| ① 取り込む | `npm install` | エラーなく終わる |
| ② 環境変数を入れる | `.env.example` を `.env.local` という名前でコピーし、値を入れる（変数の一覧は[第5章 環境変数](#5-環境変数)） | 値は Git に入らない |
| ③ DB を用意する | `supabase/migrations/` のファイルを、古い順に Supabase へ適用する。Supabase の Authentication 設定で、公開サインアップ（Allow new users to sign up）をオフ、パスワードの最小文字数を8にする | テーブルができ、誰でもアカウントを作れない状態になる |
| ④ 最初の管理者を作る | 自分のターミナルで `npm run admin:first -- --shop お店の名前 --email メールアドレス --name 表示名` | 「管理者を作成しました」と一時パスワード（16文字）が1回だけ出る。控えて本人に渡す（会話や記録に貼らない） |
| ⑤ 起動する | `npm run dev` → ブラウザで `http://localhost:3000` | ログイン画面が出る |
| ⑥ CSV を取り込む | ログインし、お手元の売上 CSV（または動作確認用の同梱ダミー `tests/fixtures/lumina-sample-sales.csv`）をアップロード | 「○行 成功 / ×行 スキップ」が出る |

- 動作確認に使う CSV：本番版は `tests/fixtures/lumina-sample-sales.csv`、デモ版の見本は `demo/public/sample-sales-demo.csv`（別のファイルで、数字も違います）。`tests/fixtures/` のほかのファイルは自動テスト用です（[tests/fixtures/README.md](../tests/fixtures/README.md)）

- ④ の補足：有効な管理者がすでにいるお店では、何もせず止まります（終了コード1）。登録に失敗して作りかけのアカウントが残ったら、メッセージに従って Supabase の管理画面で削除します
- ④ で使う `SUPABASE_SERVICE_ROLE_KEY` は絶対に隠すキーです。自分の端末の `.env.local` だけに置きます

## 3. テストのコマンドと CI・Deploy の流れ

### テストのコマンド

| コマンド | 内容 |
|---|---|
| `npm run test` | 単体テスト（集計の正解値・CSV・AI の照合など）。AI は呼ばず、固定の応答を使う |
| `npm run test:rls` | 権限（RLS）テスト。他のお店のデータが0件・操作者が管理者の処理を実行できない、など。Supabase とテスト用アカウントが必要 |
| `npm run test:e2e` | 画面の流れ（ログイン・取り込み・ダッシュボード・スマホ幅） |
| `npm run lint` ・ `npm run type-check` | コードの検査・型の検査 |

- 集計の正解値テストは、同梱のダミー CSV（本番版用 `tests/fixtures/lumina-sample-sales.csv`）の数字（売上は9月 95,500 円・10月 92,000 円・11月 253,500 円、リピート率の期間全体は 40.0% など）を、手計算で決めて固定しています（`tests/unit/lumina-sample-csv.test.ts`）。テストを通すために正解値を書き換えず、合わないときは実装を疑ってください
- 講座の配布 CSV はこのリポジトリに含めていません（権利は講座の提供元にあります）。本番版の正解値の確認は、非公開の作業用リポジトリで行っています

### CI と Deploy の流れ

CI は、コードを自動で検査する仕組み（GitHub Actions）です。

| ワークフロー | いつ動く | 内容 |
|---|---|---|
| CI | main 以外のブランチへの push・プルリクエスト・手動 | 型チェック・Lint・単体テスト／権限テスト（実行の中で使い捨ての Supabase を起動する。本物のキーは使わない） |
| Deploy | main への push・手動 | まず CI を全部実行し、すべて合格したときだけ Vercel の本番へ公開する |
| Supabase 停止防止 | 毎日1回・手動 | 軽い DB 関数を呼ぶ（第4章） |

- CI のテストでは、実際の AI を呼びません（無料枠の回数を使わないため）
- Deploy と Supabase 停止防止は、本番を運用する作業用リポジトリにだけあります（第4章）

## 4. 定期の運用

> **この章は、本番を運用する作業用リポジトリでの手順です。公開リポジトリには含まれません（deploy.yml・keepalive.yml・本番の Secrets は公開側に置きません）。**

### 4-1. VERCEL_TOKEN の期限と更新

`VERCEL_TOKEN` は、GitHub Actions が Vercel へ公開するための鍵で、**有効期限があります。**

| 項目 | 内容 |
|---|---|
| 現在の期限 | **2026-11-27**（更新したら、ここを新しい期限に書き換える） |
| 切れるとどうなる | 「Deploy」が赤になり、新しい変更が公開されない。今公開されているアプリは動き続ける |
| 範囲 | Vercel のチーム全体（**All Projects**）。個別のプロジェクトだけを選ぶと、公開の途中で失敗する |

更新の手順（期限の前に行う）：

| 何をする | どう操作する | OK の目安 |
|---|---|---|
| ① 新しいトークンを作る | Vercel にログイン → Settings → Tokens → 新規作成。範囲（Scope）は **チーム全体の「All Projects」**、有効期限を決める | 作成直後にトークンの値が1回だけ出る。**その場でコピーする**（値は画面以外に貼らない） |
| ② GitHub Secrets を入れ替える | GitHub のリポジトリ → Settings → Secrets and variables → Actions → `VERCEL_TOKEN` を開いて値を新しいものに更新 | 更新した日時が変わる |
| ③ 公開できるか確かめる | リポジトリの Actions タブ → 「Deploy」→ Run workflow | 緑になる。赤で「Could not retrieve Project Settings」と出るときは、トークンの範囲が個別のプロジェクトになっていないか確かめる |
| ④ 古いトークンを消す | Vercel の Tokens で、古いトークンを削除 | 一覧から消える |

### 4-2. Supabase を有料プラン（Pro 以上）に上げるとき

今は無料プランのため、「漏えいしたパスワードの確認」（流出済みのパスワードを使わせない機能）はオフです。代わりに、パスワード8文字以上・一時パスワードは16文字のランダム・公開サインアップなしで守っています。

有料プラン（Pro 以上）に上げたら、**この確認をオンにします。**

| 何をする | どう操作する | OK の目安 |
|---|---|---|
| オンにする | Supabase のダッシュボード → 対象のプロジェクト → Authentication → Attack Protection →「Prevent use of leaked passwords」（今は DISABLED）。右の「Configure in email provider」から入り、オンにする | 設定が保存される |
| 動作を確かめる | 管理者画面でテスト用のメンバーを追加し、ログイン後のパスワード変更で、よくある弱いパスワードを入れる | 拒否される |

- 画面の場所は、2026年10月に Supabase のダッシュボードで確認しました（無料プランでは DISABLED のまま）。画面の名前は変わることがあるので、見つからないときは Supabase の公式資料（Password security）を見てください

### 4-3. 停止防止（keepalive）の見かた

Supabase の無料プランは、1週間ほど動きがないと一時停止されることがあります。これを避けるため、GitHub Actions が**毎日1回**（日本時間 12:17 ごろ・多少遅れることがあります）、データを読まない軽い関数 `keepalive()` を呼びます。これで停止を防げる保証はありませんが、たいていは足ります。

| 何をする | どう操作する | OK の目安 |
|---|---|---|
| 毎日の動きを見る | リポジトリの Actions タブ →「Supabase 停止防止（毎日）」 | 最新の実行が緑のチェック |
| 今すぐ動かす | 同じ画面の Run workflow を押す | 緑になる |
| 赤のとき | 赤い実行を開き、「keepalive() のステータスコード」を見る | 下の表で原因を絞る |

| ステータスコード | 原因 | 直し方 |
|---|---|---|
| 401 | 公開キーが違う | GitHub Secrets の `NEXT_PUBLIC_SUPABASE_ANON_KEY` を入れ直す |
| 404 | DB に `keepalive()` 関数がない | マイグレーションの適用漏れ。`supabase/migrations/` を確かめる |
| 000 | 通信できない | 時間をおいて、Run workflow でもう一度動かす |

- Supabase が一時停止していたら、ダッシュボードでプロジェクトを選び、「Resume project」を押すと再開できます（停止から90日以内。公式 supabase.com/docs/guides/platform/free-project-pausing で2026-10-29 に確認）
- GitHub は、公開リポジトリに60日間動きがないと、定期実行を自動で止めます（公式 docs.github.com の schedule イベントで2026-10-29 に確認。非公開リポジトリについては記載なし）。止まっていたら、Actions タブで有効に戻します

## 5. 環境変数

このアプリが使う環境変数の「名前」と「入れ方」の一覧です。**値はこの資料に書きません。**
対象：保守担当。手元での動かし方は[第2章](#2-手元で動かす)を見てください。
GitHub Secrets と Vercel の項目は、本番を運用する作業用リポジトリでの設定です（公開リポジトリには本番の Secrets を置きません）。

### 5-1. 守ること

- 値は、チャット・メール・README・スクリーンショット・Git に書きません。入れる場所は次の3か所だけです
- 「公開可」以外の値が漏れたときは、発行元（Supabase・Google・Anthropic・Vercel）でキーを作り直して入れ替えます
- `.env.local` は Git に入りません。`.env.example` には名前だけが入っています

### 5-2. どこに入れるか

| 場所 | 使うとき | 入れ方 |
|---|---|---|
| `.env.local`（手元のパソコン） | 開発・テスト | `.env.example` を `.env.local` という名前でコピーし、各行の `=` の右に値を入れる。保存したら開発サーバーを再起動 |
| Vercel の環境変数（本番） | 本番アプリ | Vercel のプロジェクト → Settings → Environment Variables → 名前と値を入れて保存 → 反映のため、GitHub の Actions タブで「Deploy」を手動実行する |
| GitHub Secrets | 自動の公開・停止防止 | GitHub のリポジトリ → Settings → Secrets and variables → Actions → New repository secret → 名前と値を入れて保存 |

OK の目安：本番は、Deploy が緑になり、ログインとダッシュボードが開けること。

### 5-3. 一覧

#### アプリが使うもの

| 変数名 | 用途 | 公開 | 入れる場所 | 値の取り方 |
|---|---|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase の URL | 可 | `.env.local`・Vercel・GitHub Secrets（停止防止が使う） | Supabase のプロジェクト設定の API の画面 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase の公開キー（行ごとのアクセス制限が前提） | 可 | `.env.local`・Vercel・GitHub Secrets（停止防止が使う） | 同上 |
| `SUPABASE_SERVICE_ROLE_KEY` | 管理者画面の処理（メンバー追加・一時パスワードの再発行・状態の変更）・テスト | **不可（絶対に隠す）** | `.env.local`・Vercel | 同上。サーバー側だけで使う。ブラウザ・ログに出さない。漏れると全データが読まれる |
| `LLM_PROVIDER` | AI 分析に使うサービス。`claude` か `gemini`（手動で切り替える。自動では切り替わらない） | 可 | `.env.local`・Vercel | 検証環境は `gemini` |
| `ANTHROPIC_API_KEY` | Claude API（本番用） | **不可** | `.env.local`・Vercel（`claude` を使うときだけ） | Anthropic のコンソールで発行 |
| `GEMINI_API_KEY` | Gemini API（検証用） | **不可** | `.env.local`・Vercel（`gemini` を使うときだけ） | Google AI Studio で発行 |
| `GEMINI_MODEL` | Gemini のモデルを切り替える（任意）。`gemini-3.5-flash-lite`（既定）か `gemini-3.8-flash` だけ | 可 | `.env.local`（任意） | 空のままなら既定のモデル。ほかの値は、日本語のエラーで止まる |

Vercel に入れるのは、Supabase の3つ・`LLM_PROVIDER`・使う AI のキーの合計5つです。

#### 自動の公開に使うもの（GitHub Secrets だけ）

| 変数名 | 用途 | 公開 | 値の取り方 |
|---|---|---|---|
| `VERCEL_TOKEN` | GitHub Actions から Vercel へ公開する鍵。**有効期限があります** | **不可** | Vercel の Settings → Tokens で作成。更新の手順は[4-1. VERCEL_TOKEN の期限と更新](#4-1-vercel_token-の期限と更新) |
| `VERCEL_ORG_ID` | Vercel のチーム（またはアカウント）の ID | 不可（公開は避ける） | Vercel のチームの設定画面 |
| `VERCEL_PROJECT_ID` | Vercel のプロジェクトの ID | 不可（公開は避ける） | Vercel のプロジェクトの Settings |

#### テストだけに使うもの（`.env.local` だけ・本番には入れない）

| 変数名 | 用途 |
|---|---|
| `TEST_ADMIN_EMAIL`・`TEST_ADMIN_PASSWORD` | 権限テスト・画面確認用の管理者アカウント |
| `TEST_OPERATOR_EMAIL`・`TEST_OPERATOR_PASSWORD` | 同じく操作者アカウント |
| `TEST_OTHER_SHOP_EMAIL`・`TEST_OTHER_SHOP_PASSWORD` | 同じく「別のお店」のアカウント（他のお店のデータが見えないことの確認用） |

テスト用のアカウントは検証用のプロジェクトにだけ作ります。本番のアカウントを使いません。

### 5-4. 入れ忘れ・入れ間違いのときの症状

| 症状 | 疑うもの |
|---|---|
| ログインできない・画面が真っ白 | `NEXT_PUBLIC_SUPABASE_URL`・`NEXT_PUBLIC_SUPABASE_ANON_KEY` |
| 管理者画面でメンバー追加・再発行が失敗する | `SUPABASE_SERVICE_ROLE_KEY` |
| 「AI分析を生成できませんでした」が続く | `LLM_PROVIDER` と、使う側のキー（`GEMINI_API_KEY`／`ANTHROPIC_API_KEY`）。Gemini の無料枠は1日の回数に上限があります |
| Deploy が赤（`vercel pull` の段階で失敗） | `VERCEL_TOKEN` の期限切れ・権限、`VERCEL_ORG_ID`・`VERCEL_PROJECT_ID` |
| 停止防止（毎日）が赤 | GitHub Secrets の `NEXT_PUBLIC_SUPABASE_URL`・`NEXT_PUBLIC_SUPABASE_ANON_KEY` |

## 6. 管理者がいなくなったとき

[運用マニュアル](operations-manual.md)の第7章（管理者が交代するとき）から、保守担当に相談が来たときの資料です。

困るのは、ただ1人の管理者が辞めて連絡が取れないときや、パスワードを忘れたときです。その間は、誰もメンバーの追加や一時パスワードの再発行ができません。最後の有効な管理者は、画面からも DB の仕組みからも、休職・退職・操作者にできないため、「管理者が0人」にはなりません。管理者はいるのに、使える人がいない状態になります。

| 項目 | 内容 |
|---|---|
| 予防 | 管理者を2人以上にしておく（運用マニュアル第7章） |
| 今の対応 | **このリポジトリには、この状態から戻す手順がありません（未対応）。** 開発者に相談する |
| 次の候補（v1.0） | 保守担当が使う、管理者の一時パスワードを再発行するコマンド（v1.0 の候補として記録済み） |

以降は、別の場合の資料です。最初の管理者を作るコマンド `npm run admin:first`（第2章の④）を、有効な管理者が1人もいないお店で使う手順です。

### 6-1. このコマンドで直せる場合・直せない場合

コードで確かめた条件です（`src/lib/admin/first-admin.ts`。単体テスト `tests/unit/first-admin.test.ts` で確認）。

| お店の状態 | コマンドの結果 |
|---|---|
| 有効な管理者（ロールが管理者で、状態が「有効」）が1人もいない | 新しい管理者を作る（直せる） |
| 有効な管理者がすでにいる（ただ1人の管理者がログインできない場合を含む） | 何も作らず・何も変えずに止まる（終了コード1）。このコマンドでは直せません（上の表の「今の対応」） |
| 新しい管理者のメールアドレスと同じアカウントがすでにある（退職した人のアドレスも含む） | 何も作らずに止まる。別のメールアドレスを使う |
| `--shop` の名前が、既存のお店の名前と違う | **別の新しいお店が作られ**、そこに管理者ができる。元のお店のデータは見えない |

- お店の名前は一字一句そろえます（空白・大文字小文字も含む）。確かめ方は下の手順①
- 「有効な管理者がいない」状態は、DB の仕組みで、画面の操作や管理用キーの更新では作れません（最後の有効な管理者を、休職・退職・ロール変更・削除にする変更は、DB が止めます。テスト `tests/integration/admin.test.ts` の「DBのトリガー」で確認）。この手順を使うのは、お店のメンバーが全員いなくなった、DB を直接操作して管理者がいなくなったなど、まれな場合に限られます
- 管理者が1人残っていてログインできない場合は、このコマンドは止まります。復旧の手順は今はありません（本章の冒頭）

### 6-2. 手順

| 何をする | どう操作する | OK の目安 |
|---|---|---|
| ① お店の名前を確かめる | Supabase のダッシュボード → Table Editor → `shops` の `name` を見る | 名前が分かる（コピーしておく） |
| ② 管理者がいないことを確かめる | Table Editor → `profiles` で、そのお店（`shop_id` が①の `id`）の中に、`role` が `admin` かつ `status` が `active` の行がないことを見る | 該当の行がない |
| ③ コマンドを実行する | 自分のターミナルで `npm run admin:first -- --shop お店の名前 --email 新しい管理者のメールアドレス --name 表示名`（`.env.local` に `NEXT_PUBLIC_SUPABASE_URL` と `SUPABASE_SERVICE_ROLE_KEY` が必要。第5章） | 「お店：既にある」と「管理者を作成しました」、一時パスワード（16文字）が1回だけ出る |
| ④ 本人に渡す | 一時パスワードを控え、本人に直接伝える（チャット・記録に貼らない） | 本人が一時パスワードでログインでき、パスワード変更の画面が出る |
| ⑤ 後始末 | 新しい管理者が、管理者画面で、元の管理者の状態を確かめる（退職のままでよい）。必要なら新しい管理者をもう1人追加する | 管理者が2人以上いる |

- ③で「お店を作成しました」と出たら、お店の名前が違っていた可能性があります。元のお店ではないので、使わずに止め、Supabase の `shops` を見て名前を確かめ直します
- ③で「すでに有効な管理者がいるため、何もしませんでした」と出たら、②の見落としです。管理者がいる状態なので、この手順は終わりです
- コマンドが途中で失敗したときは、画面に出る日本語のメッセージに従います（作りかけのアカウントは、コマンドが自動で削除します。削除にも失敗したときは、Supabase の Authentication → Users で手動で削除します）
